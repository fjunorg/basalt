# 04 · 前端 UI 技术选型评估

> 前置决策：框架技术栈收敛为 **纯 Go**（原 Ruby L3 层移除，见本文第 7 节架构影响）
> 评估对象：框架配套管理后台（Admin Console）的前端技术方案
> 版本：v0.1 · 2026-10-27 · 关联：`01-architecture.md`

---

## 1. 结论（TL;DR）

**主路线：Vue 3 + TypeScript + Vite + Element Plus，构建产物 `go:embed` 嵌入 Go 二进制，单文件交付。**

| 决策项 | 结论 | 一句话理由 |
|--------|------|-----------|
| 前端框架 | **Vue 3**（默认）/ React（生态位预留） | 国内 B/G 端事实标准，目标用户零心智迁移 |
| UI 组件库 | **Element Plus** | 2025-2026 维护最活跃；AntD Vue 有维护放缓风险；Naive UI 单人维护 |
| 构建 | Vite + TypeScript | 标准 |
| 交付形态 | **go:embed 单二进制**（开发时前后端分离） | G 端私有化盒子场景的杀手级特性 |
| 轻前端备选 | templ + HTMX（可选模块） | 零 Node 依赖的极简形态，仅覆盖简单场景 |

---

## 2. 第一层评估：前端形态三条路线

| 路线 | 方案 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **A. SPA + go:embed** | Vue 3 SPA，构建产物嵌入 Go 二进制 | 复杂中后台（表格/表单/流程设计器/权限树）唯一撑得住的路线；开发时前后端分离体验好；交付时单文件 | 需要 Node 工具链参与 CI；二进制体积 +5~15MB | ✅ **主路线** |
| B. Go 原生轻前端 | templ + HTMX + Alpine.js | 零 Node 依赖、类型安全模板、Go 全栈；单二进制最纯净 | B/G 端管理后台的复杂交互（流程设计器、拖拽表单、大表格虚拟滚动）生态撑不住；偏离国内用户习惯，学习成本转嫁给使用者 | ⚠️ 作为**可选模块**（`mod-leanui`），覆盖内网简单运维页/盒子初始化页，不承担主 UI |
| C. 双前端并行 | A + B 同时维护 | 理论上两全 | 双倍维护成本，MVP 阶段自杀式选择 | ❌ 否决 |

> 调研依据：Go 社区 embed 前端已是成熟实践（Alex Edwards、 templ+HTMX 均有生产案例），Reddit r/golang 讨论确认其适合 admin dashboard 场景——但仅限"简单后台"。B/G 端平台的完整控制台（含 AI 对话、流程设计）必须走 SPA。

## 3. 第二层评估：组件库对比（若选 Vue 3）

| 组件库 | 维护健康度 | B/G 端生态 | 人才/资料 | 协议 | 判定 |
|--------|-----------|-----------|----------|------|------|
| **Element Plus** | ✅ **最活跃**（TS 编写，持续迭代） | ✅ 若依/芋道/gin-vue-admin 全系采用，模板/低代码生态最广 | ✅ 国内最大 | MIT | ✅ **默认选择** |
| Ant Design Vue | ⚠️ 社区担忧维护节奏放缓（精力转向付费 Pro 版，V2EX 2025 讨论），React 版与 Vue 版不同团队 | ✅ JeecgBoot 采用，Table/Form 能力标杆 | ✅ 大 | MIT | 备选（设计规范要求高时） |
| Naive UI | ⚠️ 个人主导（07akioni），Bus Factor 风险 | ⚠️ 企业案例少 | ⚠️ 较小 | MIT | 不作默认（技术优秀但框架级选型不能赌单人库） |
| Arco Design Vue（字节） | ✅ 活跃 | ⚠️ 生态绑定字节系 | 中 | MIT | 备选 |
| React + Ant Design | ✅ 最活跃（antd 原生团队） | 国际主流、国内 B 端常见 | ✅ 国际最大 | MIT | **生态位预留**：若未来国际化，AntD 设计语言与 Element Plus 的 API 风格可通过封装层对齐，见第 6 节 |

**关键判定依据**：我们的框架用户要拿它做二次开发——组件库的**可招性、资料量、模板生态**比组件本身的精致度更重要。这一点上 Element Plus 无争议地领先（调研中社区共识：在意长期维护选 Element Plus）。

## 4. 模板基线参考（不从零造轮子）

| 开源模板 | 技术栈 | 协议 | 参考价值 |
|---------|--------|------|---------|
| **vue-pure-admin** | Vue3 + Vite + TS + Element Plus | MIT | **主要参考**：结构清晰、提供精简版（thin），与我们的选型完全一致 |
| Vben Admin (v5) | Vue3 + Vite + TS + AntD Vue，Monorepo | MIT | 架构参考：Monorepo 应用分层、权限方案、微前端（wujie）支持 |
| soybean-admin | Vue3 + Naive UI | MIT | 视觉与工程化参考 |

**注意**：参考架构与工程实践，**不直接 fork 代码**作为框架资产——Admin Console 作为框架官方组件从第一天自研（规模可控：登录/布局/权限路由/用户/租户/审计/AI 控制台约 15-20 个页面），保证与我们 mod-codegen 生成规范完全一致。若直接 fork 模板，后续每次升级都背着合并负担。

## 5. 专项评估

### 5.1 AI 场景前端需求（L2 的 UI 面）
- **流式对话 UI**：SSE/WebSocket 渲染，Vue 生态成熟（自研组件，不用重型聊天库）
- **Markdown + 代码高亮渲染**：markdown-it + Shiki（信创环境可离线打包）
- **RAG 调试面板**：检索命中可视化（框架特色，竞品 admin 均无）
- **Prompt 管理/版本对比界面**：常规表单 + diff 组件
- 结论：Vue 生态全部可满足，无额外风险

### 5.2 信创 / G 端浏览器兼容
- 麒麟/统信自带浏览器均为 Chromium 内核（≥ 90），Vue 3 + Vite 默认目标（es2018+）兼容无虞
- Vite 构建需固定 `build.target` 与 `browserslist`（建议 chromium 90 基线），禁用过新 CSS 特性
- 前端依赖需纳入 SBOM（与治理文档 02 的供应链安全条款一致）；**禁用 CDN 运行时加载**——全部资源 embed，私有化环境无外网（这是 go:embed 路线的天然优势）

### 5.3 与 mod-codegen 的联动（选型的重要砝码）
代码生成器输出 = Go handler + OpenAPI 变更 + **Vue CRUD 页面**（列表/表单/详情三件套）。
选择 Vue 3 + Element Plus 意味着生成模板可以参考若依/gin-vue-admin 已被市场验证十年的页面范式——**生成代码的"用户熟悉度"本身是框架竞争力**。

### 5.4 微前端（P2，暂不做）
大型 B 端客户多模块插拔场景可能需要 qiankun/wujie。Vben 的 wujie 实践可后参考。MVP 阶段用"路由级模块注册"代替，架构上预留（Console 的路由表由后端模块动态下发——这个设计同时服务于权限控制）。

## 6. React 生态位预留方案

框架层定义 **UI 契约**（页面区块协议：路由/菜单/权限点/组件槽位均由后端 OpenAPI 下发），官方 Console 用 Vue 实现。社区未来可贡献 React 版 Console（契约兼容即可替换）——花小成本设计契约，换取国际生态可能性，而不承担双前端维护。

## 7. 对架构文档 01 的影响（同步修改）

| 原设计（v0.1） | 变更后 |
|----------------|--------|
| L3 效率层 = Ruby on Rails（console/forge/seedlab） | **删除**。技术栈收敛为纯 Go |
| console（运营后台） | → **L3 前端控制台层**：Vue 3 + Element Plus SPA，go:embed 托管 |
| forge（工具生成）/seedlab（数据工厂） | → 并入 `kernel-cli`（Go CLI 子命令） |
| 双语言协同铁律（OpenAPI 契约/禁直连库） | 简化为**单一协同规则**：前端只经 OpenAPI 访问后端，构建产物 embed 进二进制 |
| 风险"双语言社区认知成本" | 移除，替换为"前端组件库维护风险"（缓解：组件抽象层 + 备选库兼容设计） |
| 设计原则 P1"Go 承诺，Ruby 特色" | 改为"**纯 Go 单二进制交付**" |
