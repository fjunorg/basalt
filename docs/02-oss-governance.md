# 02 · 开源协议与社区治理设计

> 关联文档：`01-architecture.md`（架构设计）、`03-gap-analysis.md`（竞品差距分析）
> 版本：v0.1（治理草案）· 2026-10-27
> 核心立场：**纯开源，永不出闭源/阉割"商业版"**。商业化 = 服务，不是功能。

---

## 1. 协议选择：Apache License 2.0（推荐，而非 MIT）

| 对比项 | Apache 2.0 ✅ | MIT |
|--------|--------------|-----|
| 专利授权 | **显式授予 + 专利报复条款** | 无 |
| 企业采购法务审查 | B/G 端客户法务最熟悉、最容易过 | 也容易，但大公司法务对无专利条款更谨慎 |
| 商标保留 | 协议明确不含商标 | 需额外声明 |
| 修改声明义务 | 有（NOTICE 文件） | 无 |

**决策理由**：
1. 框架内置国密实现与 AI 能力，下游（尤其信创集成商）会深度魔改分发，Apache 2.0 的专利条款消除他们被诉的顾虑——**这直接影响 ToB/ToG 客户的采用意愿**；
2. 协议不可附加限制条款（**不做 Dify 式"开源但限制商用/多租户"的修改版协议**）——这是调研确认的差异化卖点：客户采购合规审查零障碍；
3. 商标不随代码开源，注册商标保护项目名，防止被集成商 fork 换皮售卖（Java 竞品区常见的乱象）。

**落地清单**：
- [ ] 仓库根目录放置标准 `LICENSE`（Apache 2.0 官方全文，不得改动）
- [ ] `NOTICE` 文件：声明版权、商标、第三方组件清单（依赖 Eino/emmansun/gmsm 等的协议均需列明并确认兼容性——Eino 为 Apache 2.0 ✅，emmansun/gmsm 为 Apache 2.0 ✅）
- [ ] 国内商标注册（第 9/42 类：软件、技术服务），框架名定稿后立即申请

## 2. 贡献者协议：DCO 为主，CLA 为辅

**推荐组合：企业级贡献需 CLA，个人贡献走 DCO。**

| 机制 | 适用对象 | 说明 |
|------|---------|------|
| **DCO**（Developer Certificate of Origin） | 个人贡献者 | `git commit -s` 签名即可，零摩擦，社区友好 |
| **CLA**（个人 + 企业两种） | 提交量大的贡献者 / 公司员工贡献 | 保护项目版权清洁，为未来转入基金会做准备 |

**为什么需要企业 CLA**：信创集成商会派工程师贡献国产数据库驱动等代码。没有企业 CLA，其雇主可能事后主张版权，污染项目。使用 CLA Assistant（GitHub 集成，免费）或 EasyCLA（Linux 基金会，未来转基金会时平滑迁移）。

### CLA 核心条款要点（法务起草时的需求清单）
1. 贡献者授予项目永久、全球、免费、可再许可的版权许可（不是转让，社区接受度高）；
2. 同样的专利许可授予；
3. 企业 CLA 需签署人确认有权代表雇主；
4. **项目方承诺：所有贡献只以 Apache 2.0（或更新版本）分发**——写进 CLA 是对贡献者的反向承诺，强化"纯开源不可逆"。

## 3. 仓库治理文件骨架（可直接落库）

```
仓库根/
├── LICENSE                  # Apache 2.0 全文
├── NOTICE                   # 版权/商标/第三方清单
├── CONTRIBUTING.md          # 贡献指南
├── CODE_OF_CONDUCT.md       # Contributor Covenant 2.1（中英双语）
├── SECURITY.md              # 安全披露流程（ToG 重中之重）
├── GOVERNANCE.md            # 社区治理章程（本文档第 4 节落地版）
├── OPEN_SOURCE_PLEDGE.md    # 纯开源承诺书（营销+法律双重作用）
└── docs/adr/                # 架构决策记录
```

### 3.1 CONTRIBUTING.md 要点骨架
- 环境要求：Go ≥ 1.23 / Ruby ≥ 3.3，`make dev` 一键起环境
- 分支模型：trunk-based（短分支 + 频繁合并），保护 main 分支
- PR 门禁：CI 必过（编译 × 交叉编译矩阵 ARM/LoongArch、多数据库测试矩阵、lint、架构守护测试——包括"Ruby 层不得直连数据库"的依赖规则检查）
- 提交规范：Conventional Commits；**DCO 签名必需**（`-s`）
- 新模块提案流程：先提 RFC（`docs/rfcs/` 模板：问题/方案/替代方案/影响面），两名 maintainer 批准

### 3.2 SECURITY.md 要点（ToG 框架的生死线，若依的教训）
- **私有披露**：安全邮箱 security@（私有 inbox），**禁止在公开 issue 报安全漏洞**
- 响应 SLA：确认 ≤ 48h，修复目标：严重漏洞 ≤ 7 天
- **等保特殊性**：漏洞修复需附"影响等级评估（CVSS）+ 等保映射说明"，方便 G 端客户走内部整改流程
- 已修复漏洞披露策略：修复后 90 天公开细节 + CVE 申请
- **默认安全基线文档**：安装即等保参考配置（默认口令禁用、初始密钥强制轮换——直击若依默认密钥漏洞的行业事故）

### 3.3 OPEN_SOURCE_PLEDGE.md（纯开源承诺书）——差异化武器
公开承诺四条：
1. 框架全部功能以 Apache 2.0 开源，**永远不存在仅限付费用户的闭源功能模块**；
2. 文档、示例、脚手架与代码同仓库同协议，不搞"文档收费"；
3. 版本无社区版/企业版之分，仅有支持服务的商业区别；
4. 若项目停止维护，代码捐赠给中立基金会（Apache/CNCF/OpenAtom 开放原子，国内 ToG 场景优先开放原子）。

> 这是直接打向 JeecgBoot（开源版功能少 30%）和 BladeX（闭源）的营销差异化，也是 G 端客户"自主可控"叙事的最强背书。

## 4. 社区治理模式（三阶段演进）

| 阶段 | 触发条件 | 治理结构 |
|------|---------|---------|
| **孵化期**（M1–M2，0–6 月） | 核心团队 < 10 人 | BDFL（发起人最终决策权）+ 2–3 名 maintainer；决策记录全走 ADR/RFC 公示 |
| **成长期**（star > 5k 或 ≥ 3 家企业生产使用） | 外部 maintainer 出现 | **技术委员会**（5 席：发起方 2 + 社区选举 2 + 企业会员 1），RFC 投票制 |
| **成熟期** | 多家厂商形成生态 | 捐赠至基金会（国内：**开放原子开源基金会**——ToG 采购方认可度最高；国际：CNCF/Apache），发起公司转为首要贡献者 |

**维护者晋升路径**：贡献者 → reviewer（某模块）→ maintainer → 技术委员会，每级标准写入 GOVERNANCE.md（可量化：review 数、PR 数、模块熟悉度）。

### 4.1 版本策略（为 ToG 客户专门设计，竞品普遍没做好）

- 语义化版本（SemVer），**每年一个 LTS 版本，安全维护承诺 3 年**（G 端项目生命周期长，Java 竞品的随意升级节奏是被诟病的痛点）；
- 升级保证：minor 版本零破坏性变更，提供迁移工具（CLI 内置 `basalt migrate`）；
- **供应链安全**：每次 release 附 SBOM（CycloneDX）、签名（cosign + Sigstore）、可复现构建（reproducible build）——G 端等保和密码应用评估的实际加分项。

### 4.2 核心团队保护条款（防"被项目掏空"）
发起公司内部制度（写入 GOVERNANCE 附录）：
- 核心团队 **≥ 60% 工时投入框架主线**，定制项目人员单列；
- 所有定制项目产出的通用代码 **30 天内必须回馈主干**（客户 NDA 允许范围内），防止主干/私有分叉漂移；
- 商业服务定价公开（见第 5 节），避免销售层把"开源免费"卖成"商务惊喜"。

## 5. 商业模式设计（纯开源下的收入引擎）

**原则：卖的是"省心"，不是"功能"。** 参照红帽（订阅）+ Rails Foundation（会员）+ 芋道（轻服务）验证过的路径：

| 收入线 | 定价模型 | 参照 | 启动时机 |
|--------|---------|------|---------|
| **企业支持订阅**（工单 SLA、补丁、升级护航、信创适配认证支持） | 按年/按实例 | 红帽模式 | M3 后 |
| **培训与认证**（工程师认证：Basalt Certified Engineer） | 按人/按企业内训 | 红帽认证体系 | M3 后 |
| **托管 SaaS**（框架即服务，B 端中小客户） | 按用量 | Discourse/GitLab 模式 | 1.0 稳定后 |
| **企业会员**（LOGO 展示、路线图席位、优先 support） | 年费制 | Rails Foundation | 成长期 |
| **G 端定制实施** | 项目制 | 芋道模式 | 立即（养团队） |

> ToG 采购现实：政府/国企有"运维服务""安全加固""适配认证"预算科目，**纯开源 + 服务订阅完全能承接**，且"自主可控"使开源在 G 端招标反而是加分项（可写进招标参数的"源代码可得性"条款）。

## 6. 治理风险登记

| 风险 | 缓解 |
|------|------|
| 发起公司被收购后协议私有化转向（MongoDB/Elastic 教训） | 纯开源承诺书 + CLA 反向条款 + 成熟期捐赠基金会，法律与社区双重锁定 |
| 商标被抢注/集成商换皮售卖 | 协议不含商标 + 提前注册商标 + NOTICE 声明 |
| DCO/CLA 流程劝退贡献者 | 个人走 DCO（一个 `-s` 搞定），CLA 只对企业和高频贡献者 |
| 双语言社区割裂 | 贡献指南明确：Go 层接受度优先，Ruby 层定位"进阶贡献区" |
